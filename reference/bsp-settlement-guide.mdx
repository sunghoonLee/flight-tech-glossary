## 1. BSP 개요

### BSP (Billing and Settlement Plan)

IATA가 운영하는 **항공사와 여행사 간의 대금 정산 중개 시스템**.

```
BSP 없을 때:
  여행사 100개 × 항공사 50개 = 5,000개의 개별 정산 관계

BSP 있을 때:
  여행사 A ──┐                ┌──→ 대한항공
  여행사 B ──┼──→ [BSP] ──→──┼──→ 아시아나
  여행사 C ──┘                └──→ 싱가포르항공

  → 여행사는 BSP 하나에만 정산
  → 항공사도 BSP 하나에서만 수금
```

## 2. BSP 동작 흐름

```
1. 발권
   고객 → 여행사 → GDS에서 항공권 발권

          │
          ▼
2. 리포팅 (Reporting)
   발권 데이터가 BSP로 자동 전송
   ┌────────────────────────────────┐
   │ BSP 리포팅 데이터               │
   │ - 항공권 번호                    │
   │ - 발권 여행사 (PCC/OID)         │
   │ - 항공사 코드                    │
   │ - 운임 금액                      │
   │ - 수수료                        │
   │ - 발권일                        │
   └────────────────────────────────┘

          │
          ▼
3. 빌링 (Billing)
   BSP가 정산 주기마다 청구서 생성
   ┌────────────────────────────────┐
   │ 여행사 A 청구서                  │
   │ - 대한항공 항공권 5건: 500만 원   │
   │ - 아시아나 항공권 3건: 300만 원   │
   │ - 수수료 차감: -40만 원          │
   │ ─────────────────────────      │
   │ 총 납부액: 760만 원              │
   └────────────────────────────────┘

          │
          ▼
4. 정산 (Settlement)
   여행사 → BSP 계좌로 입금 → BSP가 각 항공사에 분배
```

### 정산 주기 (Remittance Period)

```
한국 BSP 정산 주기 (예시):

  1일 ─────── 15일 ─────── 말일
  │← 1차 정산 기간 →│← 2차 정산 기간 →│

  1차: 1일~15일 발권분 → 약 20일경 정산
  2차: 16일~말일 발권분 → 약 다음달 5일경 정산

  HOT (Handing Over Time): BSP 데이터 마감 시점
  RD (Remittance Date): 실제 대금 납부일
```

```

│                                                      │
│  ┌──────────┐    ┌─────────┐    ┌──────────────┐     │
│  │ 항공사    │    │  BSP    │    │ 여행사/대리점  │     │
│  │(Carrier) │←──→│(정산소) │←──→│(Agent)       │     │
│  └──────────┘    └────┬────┘    └──────────────┘     │
│                       │                              │
│                  ┌────┴────┐                          │
│                  │  GDS    │                          │
│                  │(Sabre,  │                          │
│                  │Amadeus) │                          │
│                  └─────────┘                          │
│                                                      │
│  ┌──────────────┐                                    │
│  │ BSP Bank     │ ← 정산 대금 보관/이체                 │
│  │ (정산 은행)    │                                    │
│  └──────────────┘                                    │
└──────────────────────────────────────────────────────┘
```

### BSPlink

- BSP의 **온라인 포털** 시스템
- 여행사와 항공사가 접속하여 정산 내역 조회/관리

```
BSPlink에서 할 수 있는 것:
  - 발권/환불 내역 조회
  - 청구서(Billing) 확인
  - ADM/ACM 확인 및 분쟁 처리
  - 정산 리포트 다운로드
  - 항공사별 매출 현황 확인
```

## 4. 핵심 문서/전표

### 항공권 관련 전표

| 전표 | 설명 |
|------|------|
| **TKT (Ticket)** | 발권된 항공권. BSP를 통해 정산됨 |
| **EMD (Electronic Miscellaneous Document)** | 부가 서비스 전표 (수하물 추가, 좌석 업그레이드 등) |
| **MCO (Miscellaneous Charges Order)** | 기타 요금 전표 (예: 페널티) |

### 정산 조정 문서

| 문서 | 정식 명칭 | 방향 | 설명 |
|------|----------|------|------|
| **ADM** | Agent Debit Memo | 항공사 → 여행사 | 항공사가 여행사에 **추가 청구** |
| **ACM** | Agent Credit Memo | 항공사 → 여행사 | 항공사가 여행사에 **환급** |

```
ADM 발생 사례:
  - 여행사가 잘못된 운임으로 발권 → 차액 청구
  - 항공사: "운임이 50만 원인데 40만 원으로 발권했네요"
  → ADM 10만 원 발행 → BSP 정산에서 추가 차감

ACM 발생 사례:
  - 항공사 프로모션 커미션 정산
  - 항공사: "이번 달 프로모션 인센티브 100만 원 지급"
  → ACM 100만 원 발행 → BSP 정산에서 추가 입금
```

## 5. BSP 정산 계산

```
여행사 A의 1차 정산 기간 (1일~15일) 내역:

발권:
  ┌──────────┬──────────┬──────────┬──────────┐
  │ 항공권    │ 항공사    │ 운임      │ 수수료   │
  ├──────────┼──────────┼──────────┼──────────┤
  │ TKT-001  │ 대한항공  │ 150만    │ 1.5만    │
  │ TKT-002  │ 대한항공  │ 200만    │ 2.0만    │
  │ TKT-003  │ 아시아나  │ 120만    │ 1.2만    │
  │ TKT-004  │ 싱가포르  │ 300만    │ 3.0만    │
  └──────────┴──────────┴──────────┴──────────┘

환불:
  │ RFND-001 │ 대한항공  │ -150만   │ -1.5만   │  (TKT-001 환불)

ADM/ACM:
  │ ADM-001  │ 아시아나  │ +5만     │          │  (운임 차액)
  │ ACM-001  │ 대한항공  │ -10만    │          │  (프로모션)

정산 계산:
  대한항공:  200만(발권) - 150만(환불) - 10만(ACM) = 40만
  아시아나:  120만(발권) + 5만(ADM)                = 125만
  싱가포르:  300만(발권)                           = 300만
  ──────────────────────────────────────────
  총 납부액: 465만 원

  수수료:   2.0만 + 1.2만 + 3.0만 - 1.5만(환불분) = 4.7만 원
  → 수수료는 여행사 수입

  여행사 A가 BSP에 납부: 465만 - 4.7만 = 460.3만 원
  BSP가 각 항공사에 분배: 대한항공 40만, 아시아나 125만, 싱가포르 300만
```

## 6. BSP와 PCC/OID의 관계

```
PCC/OID가 BSP에서 중요한 이유:

  발권 시 PCC/OID가 기록됨
  → BSP는 어떤 PCC/OID에서 발권했는지 기준으로 정산

  PCC/OID 분리 = BSP 정산 분리

  F8UM (Offline) → BSP 정산 A (오프라인 매출)
  신규 (Online)  → BSP 정산 B (온라인 매출)

  → 채널별 BSP 정산 내역을 분리해서 볼 수 있음
```

## 7. GDS DSR과 BSP Billing 정산대사

### 두 가지 데이터 소스

#### GDS DSR (내부 기록)

```
여행사가 GDS를 통해 발권한 모든 기록

데이터 흐름:
  상담원/API → GDS에서 발권 → DSR로 데이터 전송 → 여행사 저장소

DSR 데이터:
  ┌─────────────────────────────────────────────┐
  │ 항공권 번호: 180-1234567890                    │
  │ PCC/OID: F8UM                                │
  │ 발권일: 2026-02-19                            │
  │ 항공사: KE (대한항공)                            │
  │ 구간: ICN-NRT-ICN                             │
  │ 승객: 홍길동                                    │
  │ 운임(Fare): 450,000원                          │
  │ 세금(Tax): 78,400원                            │
  │ 총액(Total): 528,400원                         │
  │ 결제수단: 카드                                   │
  │ 상태: ISSUED / REFUNDED / VOID                 │
  └─────────────────────────────────────────────┘

특징: 실시간 또는 일배치 수신, 여행사가 직접 관리하는 "원장"
```

#### IATA BSP Billing (외부 청구)

```
BSP가 정산 주기별로 여행사에 청구하는 내역

데이터 흐름:
  GDS → BSP 리포팅 → BSP 집계 → 청구서 발행 → BSPlink에서 조회

BSP Billing 데이터:
  ┌─────────────────────────────────────────────┐
  │ 정산 기간: 2026-02-01 ~ 2026-02-15           │
  │ Agent Code: 00-0 0000 0 (IATA 번호)          │
  │                                             │
  │ [발권] TKT 180-1234567890  KE  528,400원     │
  │ [발권] TKT 180-1234567891  OZ  312,000원     │
  │ [환불] RFND 180-1234567880 KE -450,000원     │
  │ [ADM]  ADM-2026-001  KE  +50,000원          │
  │ [ACM]  ACM-2026-002  OZ  -30,000원          │
  │ [수수료] Commission: -15,200원               │
  │                                             │
  │ 총 납부액: 395,200원                          │
  └─────────────────────────────────────────────┘

특징: 정산 주기(보통 2주)마다 발행, BSP가 계산한 "청구서"
```

### 정산대사 프로세스

```
┌─────────┐     ┌─────────┐     ┌─────────────┐     ┌──────────┐
│ 1. 수집  │ ──→ │ 2. 매칭  │ ──→ │ 3. 불일치   │ ──→ │ 4. 해결  │
│         │     │         │     │    분석      │     │          │
└─────────┘     └─────────┘     └─────────────┘     └──────────┘
```

### 매칭 (Matching)

```
매칭 키: 항공권 번호 (Ticket Number)

DSR                              BSP Billing
┌─────────────────────┐         ┌─────────────────────┐
│ 180-1234567890      │ ──✅──→ │ 180-1234567890      │  매칭됨
│ Total: 528,400      │         │ Total: 528,400      │
├─────────────────────┤         ├─────────────────────┤
│ 180-1234567892      │ ──❌    │                     │  DSR에만 존재
├─────────────────────┤         ├─────────────────────┤
│                     │    ❌── │ 180-1234567893      │  BSP에만 존재
├─────────────────────┤         ├─────────────────────┤
│ 180-1234567894      │ ──⚠──→ │ 180-1234567894      │  금액 불일치
│ Total: 528,400      │         │ Total: 538,400      │
└─────────────────────┘         └─────────────────────┘
```

### 불일치 4가지 유형

```
✅ Type 1: 완전 일치 (Matched)
   DSR ○  BSP ○  금액 동일 → 정상

⚠️ Type 2: 금액 불일치 (Amount Mismatch)
   DSR ○  BSP ○  금액 다름 → 원인 조사 필요

❌ Type 3: DSR에만 존재 (DSR Only)
   DSR ○  BSP ✕ → BSP 리포팅 누락 또는 VOID

❌ Type 4: BSP에만 존재 (BSP Only)
   DSR ✕  BSP ○ → DSR 수신 누락 또는 다른 PCC/OID 발권
```

### 불일치 원인과 해결

#### Type 2: 금액 불일치

| 원인 | 설명 | 해결 |
|------|------|------|
| **세금 차이** | 발권/리포팅 시점의 세금 계산 차이 | 항공사 확인 후 ADM/ACM 처리 |
| **환율 차이** | 국제선 운임의 환율 적용 시점 차이 | BSP 환율 기준으로 보정 |
| **수수료 계산** | 커미션 포함/미포함 차이 | 계약 조건 확인 |
| **재발행** | 원래 금액과 재발행 후 차액 | 재발행 이력 추적 |
| **ADM 반영** | 항공사가 운임 차액 ADM 발행 | ADM 내역 확인 |

#### Type 3: DSR에만 존재

| 원인 | 설명 | 해결 |
|------|------|------|
| **VOID 처리** | 당일 VOID → BSP에 리포팅 안 됨 | DSR에서 VOID 확인, 정상 케이스 |
| **타이밍 차이** | 마감 직전 발권 → 다음 기간 이월 | 다음 정산 기간에서 매칭 |
| **BSP 리포팅 실패** | GDS → BSP 전송 오류 | GDS/BSP 기술 지원 요청 |
| **비BSP 항공사** | BSP 비참여 항공사 (LCC 등) | BSP 대사 대상 아님 |

#### Type 4: BSP에만 존재

| 원인 | 설명 | 해결 |
|------|------|------|
| **DSR 수신 누락** | DSR 전송 실패/유실 | GDS에서 원본 데이터 재요청 |
| **다른 PCC/OID** | 다른 채널에서 발권 | PCC/OID별 크로스 체크 |
| **수동 발권** | 터미널 직접 발권 → DSR 미전송 | 수동 발권 프로세스 점검 |
| **ADM/ACM** | 항공사 발행 → DSR에 없음 | ADM/ACM 별도 대사 |

### 내부 대사 vs 외부 대사

```
1단계: 내부 대사 (DSR vs 내부 시스템)
┌───────────────────────────────────────────────┐
│ [DSR 데이터]  ←──대사──→  [내부 예약/결제 시스템] │
│                                               │
│ 체크 항목:                                     │
│ - 주문 건별 항공권 번호 매칭                      │
│ - 결제 금액 = DSR 운임 + 세금                    │
│ - 환불 처리 상태 일치                            │
│ - 고객 청구 금액 vs 항공사 정산 금액               │
└───────────────────────────────────────────────┘
       │
       ▼ 내부 정합성 확보 후

2단계: 외부 대사 (DSR vs BSP Billing)
┌───────────────────────────────────────────────┐
│ [DSR 데이터]  ←──대사──→  [BSP Billing]        │
│                                               │
│ 체크 항목:                                     │
│ - 항공권 번호 1:1 매칭                           │
│ - 운임/세금/총액 일치                            │
│ - 환불 금액 일치                                │
│ - ADM/ACM 확인 및 반영                          │
└───────────────────────────────────────────────┘
```

### PCC/OID 분리 시 대사 복잡도

```
분리 전 (단일):
  DSR (F8UM) ←──대사──→ BSP Billing (F8UM)

분리 후 (복수):
  DSR (F8UM, Offline)     ←──→  BSP Billing (F8UM)
  DSR (신규, Online)       ←──→  BSP Billing (신규 PCC)
  DSR (스카이스캐너 OID)   ←──→  BSP Billing (스카이스캐너 OID)

  + 크로스 체크:
    채널 간 오발권(잘못된 PCC/OID로 발권) 감지 필요
```

### 정산대사 타임라인

```
발권일          HOT            RD           대사 완료
  │              │              │              │
  ▼              ▼              ▼              ▼
──┬──────────────┬──────────────┬──────────────┬──→
  │   발권 기간   │  BSP 집계    │  대금 납부    │
  │              │  + Billing   │              │
  │              │  발행         │              │

예시 (한국 BSP):
  2/1~2/15:  1차 정산 기간 (발권), DSR 실시간 수신
  2/16:      HOT (BSP 데이터 마감)
  2/17~18:   BSP Billing 발행
  2/20:      RD (대금 납부)
  2/17~25:   정산대사 수행 기간
  2/25~말:   ADM/ACM 분쟁 처리 (필요 시)
```

### 자동화 대사 시스템 구성

```
[데이터 수집 레이어]
┌──────────┐  ┌──────────────┐  ┌────────────────┐
│ GDS DSR  │  │ BSP Billing  │  │ 내부 예약/결제   │
│(SFTP/API)│  │(BSPlink/API) │  │ 시스템 (DB)     │
└────┬─────┘  └──────┬───────┘  └───────┬────────┘
     │               │                  │
     ▼               ▼                  ▼
[ETL / 데이터 정제]
  - 데이터 포맷 통일 (날짜, 금액, 통화)
  - PCC/OID별 데이터 분류
  - 중복 제거, 결측 처리
                    │
                    ▼
[매칭 엔진]
  1차: 항공권 번호 정확 매칭
  2차: 금액 비교 (운임/세금/총액)
  3차: 불일치 유형 자동 분류
  4차: 알려진 패턴 자동 해소 (VOID, 타이밍, 환율 등)
                    │
                    ▼
[리포팅 / 알림]
  - 대사 결과 대시보드
  - 불일치 항목 알림 (금액 임계값 초과 시)
  - PCC/OID별 정산 현황
  - ADM/ACM 추적 리포트
  - 월별/분기별 정산 정합성 리포트
```

### 핵심 정산대사 지표

| 지표 | 설명 | 목표 |
|------|------|------|
| **매칭률** | 전체 건 중 완전 일치 비율 | 99%+ |
| **금액 일치율** | 매칭 건 중 금액 일치 비율 | 99.5%+ |
| **미매칭 건수** | DSR Only + BSP Only 건수 | 최소화 |
| **ADM 발생률** | 전체 발권 대비 ADM 비율 | 1% 미만 |
| **대사 소요일** | Billing 발행 ~ 대사 완료 | 3~5 영업일 |
| **미해결 건수** | 정산 기간 종료 후 미해결 불일치 | 0건 목표 |

## 8. 항공권 번호 체계

### 구조

```
항공권 번호: 180-1234567890 (13자리)

  180      -    1234567890
  ───           ──────────
  항공사 코드     일련번호 (10자리)
  (3자리)

항공사 코드 예시:
  180 = 대한항공 (KE)
  988 = 아시아나 (OZ)
  618 = 싱가포르항공 (SQ)
  131 = 일본항공 (JL)
```

### 체크디짓 (Check Digit)

```
일련번호 마지막 1자리는 검증용

1234567890
         └ 체크디짓: 앞 9자리로 계산된 검증값

→ 항공권 번호 입력 오류 자동 감지
→ 정산대사 시 잘못된 번호 필터링에 활용
```

### 쿠폰 (Coupon)

```
하나의 항공권에 최대 4개 쿠폰 (구간)

  TKT 180-1234567890
  ├─ Coupon 1: ICN → NRT (가는 편)    USED
  ├─ Coupon 2: NRT → ICN (오는 편)    OPEN
  ├─ Coupon 3: (미사용)
  └─ Coupon 4: (미사용)

쿠폰 상태:
  OPEN      미사용, 탑승 가능
  USED      사용됨 (탑승 완료)
  VOID      무효 처리
  REFUNDED  환불 완료
  EXCHANGED 재발행으로 대체됨
  SUSPENDED 일시 정지
```

## 9. PNR 상세 구조

### 5대 필수 요소

```
1. Name (승객명)       → HONG/GILDONG MR
2. Itinerary (여정)    → KE001 Y 15MAR ICNNRT HK1
3. Contact (연락처)    → 010-1234-5678
4. Ticketing (발권기한) → TAW/15FEB
5. Received From       → RF AGENT KIM
```

### PNR 상태 코드

```
HK  확약 (Holding Confirmed)
HL  대기 (Holding Waitlist)
HX  항공사 취소 (Cancelled by Airline)
XX  취소됨 (Cancelled)
TK  발권 완료 (Ticketed)
UC  좌석 미확정 (Unable to Confirm)
```

### PNR 생명주기

```
생성 → 확정 → 발권 → 탑승 → 완료
  │              │
  │              ├→ 변경 (재발행)
  │              ├→ 환불
  │              └→ VOID (당일 취소)
  │
  ├→ 대기 (Waitlist)
  └→ 취소 (Cancel)
```

### PNR History

```
PNR의 모든 변경 이력이 기록됨

  2/10 14:00  PNR 생성 (AGENT KIM, F8UM)
  2/10 14:05  좌석 배정 23A
  2/11 09:00  일정 변경 (3/15 → 3/20)
  2/12 11:00  발권 TKT 180-1234567890
  2/15 16:00  좌석 변경 23A → 15F

→ 정산대사 시 변경 이력 추적에 필수
→ 분쟁 발생 시 증빙 자료
```

## 10. 운임 구조 (Fare Structure)

### 항공권 금액 구성

```
총 결제 금액 = Base Fare + Tax + Surcharge + Fee

┌───────────────────────────────────────────────┐
│ Base Fare (기본 운임)          450,000원         │
│ Tax (세금/공항세)                               │
│   BP (출국납부금)              10,000원          │
│   SW (관광진흥기금)              2,000원          │
│   XT (국제관광객세)              5,000원          │
│   NR (일본 공항세)             15,400원          │
│ Surcharge (유류할증료)                          │
│   YQ (항공사 유류할증료)        46,000원          │
│   YR (항공사 기타 할증료)             0원         │
│ ─────────────────────────────────────         │
│ 총액                         528,400원         │
└───────────────────────────────────────────────┘
```

### 운임 종류

| 운임 유형 | 설명 | 특징 |
|----------|------|------|
| **Published Fare** | 항공사 공시 정가 운임 | GDS에서 조회 가능 |
| **Private Fare** | 특정 여행사/기업 계약 할인 운임 | PCC/OID에 매핑 |
| **Net Fare** | 수수료 제외한 순수 운임 | 여행사 마진 별도 |
| **IT Fare** | Inclusive Tour, 패키지 전용 운임 | 단독 판매 불가 |
| **Group Fare** | 단체 운임 (10명+ 등) | 별도 계약 필요 |

### Fare Basis Code

```
항공 운임의 규정을 나타내는 코드

  YOWKR → Y(Booking Class) + OW(편도) + KR(한국 발)
  HLE3M → H(할인 이코노미) + LE(특가) + 3M(3개월 유효)

→ FareRule 조회 시 이 코드로 환불/변경 규정 확인
→ 정산대사에서 운임 검증 시 참조
```

## 11. 발권 트랜잭션 유형

### 전체 유형

| 유형 | 설명 |
|------|------|
| **ISSUE** | 신규 발권 |
| **VOID** | 당일 무효 (발권 당일만 가능, BSP 리포팅 안 됨) |
| **REFUND** | 환불 (수수료 발생 가능) |
| **REISSUE** | 재발행 (일정/구간 변경) |
| **EXCHANGE** | 교환 (항공권 교환, 재발행과 유사) |
| **REVALIDATION** | 유효기간/편명 변경 (운임 변경 없음) |

### 정산 영향

```
ISSUE: DSR +528,400 / BSP +528,400 → 1:1 매칭

VOID:  DSR 발권+VOID 기록 / BSP 기록 없음
       → 대사 시 "DSR Only" → VOID 확인 후 정상

REFUND:
  원본 528,400 → 환불 -478,400 (수수료 50,000 차감)
  → 환불 수수료는 계약에 따라 다름

REISSUE:
  원본 TKT-001 528,400 → EXCHANGED
  신규 TKT-002 628,400 (차액 +100,000)
  → 대사 시 가장 복잡 (원본-신규 연결 필요)
```

### REISSUE 대사가 까다로운 이유

```
재발행 체인이 길어질 수 있음:

  원본 TKT-001 (528,400)
    → 재발행 TKT-002 (628,400)
      → 재발행 TKT-003 (550,000)
        → 환불 RFND-003 (-500,000)

문제점:
  - 원본/재발행 연결 정보가 BSP에서 명확하지 않을 수 있음
  - 차액 정산 vs 전액 정산 방식이 항공사마다 다름
  - 재발행 체인 전체 추적 필요
```

## 12. Queue 시스템

### Queue란?

GDS에서 여행사에 전달되는 **메시지 대기열**.

```
Queue 1:  일정 변경 알림
Queue 2:  항공사 확인/거절
Queue 3:  발권 기한 임박
Queue 7:  ADM/ACM 통보
Queue 50: 긴급 알림
```

### Queue 미처리 리스크

```
- 일정 변경 미확인 → 고객 노쇼
- 발권 기한 경과   → 예약 자동 취소
- ADM 미확인      → 정산 불일치
```

### PCC/OID와 Queue

```
각 PCC/OID마다 독립적인 Queue 존재
Branch/EOS + AQO 설정 시 연결된 PCC/OID의 Queue도 접근 가능
```

## 14. NDC (New Distribution Capability)

### 개요

IATA가 만든 **항공사-여행사 간 직접 연결 표준**.

```
기존: 항공사 → GDS → 여행사 (GDS가 중개)
NDC:  항공사 ──직접──→ 여행사 (API 직접 연결)
```

### 기존 GDS vs NDC

| 항목 | 기존 GDS | NDC |
|------|---------|-----|
| **상품 유통** | GDS 중개 | 항공사 직접 또는 NDC 어그리게이터 |
| **정산** | BSP 기반 | BSP 또는 항공사 직접 정산 |
| **발권** | GDS에서 발권 | 항공사 시스템에서 발권 |
| **수수료** | GDS 수수료 발생 | GDS 수수료 절감/없음 |

### 정산대사에 미치는 영향

```
기존: GDS 발권 → DSR → BSP → 정산대사
NDC:  항공사 직접 발권 → BSP 또는 별도 정산 → 대사 프로세스 별도 구축

→ NDC 도입 시 정산대사 시스템 확장 필요
→ 항공사마다 NDC 구현이 달라 표준화 어려움
```

## 17. Codeshare & Interline

### Codeshare (공동운항)

```
하나의 항공편에 여러 항공사 편명이 붙는 것

실제 운항: KE001 (대한항공)
공동운항: DL9000 (델타항공 편명으로도 판매)

정산 영향:
  DL9000으로 발권 → 델타항공에 BSP 정산
  델타항공이 대한항공에 운항 대가 지급
```

### Interline (타항공사 연결)

```
서로 다른 항공사 구간을 하나의 항공권으로 발권

예: ICN → NRT (대한항공) → KIX (ANA)

정산 영향:
  발권 항공사(KE)에 전체 금액 BSP 정산
  KE가 ANA 구간 운임을 ANA에 별도 정산 (Proration)
```

## 18. 여행사 수익 구조

```
1. BSP 커미션 (Commission)
   항공사 → 여행사 판매 수수료 (최근 대부분 제로 커미션)

2. 인센티브 (Incentive / Override)
   판매 목표 달성 시 항공사 추가 보상 (ACM 또는 직접 지급)

3. 서비스 수수료 (Service Fee)
   여행사 → 고객 직접 부과 (BSP 정산과 별개)

4. 마크업 (Markup)
   Net Fare에 마진을 얹어 판매 (정산가와 판매가 차액)

5. GDS 인센티브
   GDS(Sabre/Amadeus) → 여행사 사용 보상 (PCC/OID별 계약)
```

### 정산대사에서 수익 검증

```
고객 판매가    = 600,000원
BSP 정산가    = 528,400원
서비스 수수료  =  30,000원
마크업        =  41,600원

대사 포인트:
  ① 내부 결제 금액 = 600,000원 ✅
  ② DSR 총액 = 528,400원 ✅
  ③ BSP Billing = 528,400원 ✅
  ④ 수익 = 수수료 + 마크업 = 71,600원 ✅
```

## 19. 규제 및 인증

### IATA 인증 체계

| 인증 | 설명 |
|------|------|
| **IATA Accredited Agent** | IATA 공인 여행사. BSP 참여 가능 |
| **TIDS** | Travel Industry Designator Service. 비IATA 여행사 등록 |
| **GOL** | Global Online License. 온라인 여행사 전용 인증 |

### 보증금 (Financial Security)

```
BSP 참여 여행사는 보증금 예치 필요

목적: 여행사 부도 시 항공사 미수금 보전

유형:
  - Bank Guarantee (은행 보증)
  - Insurance Bond (보험 보증)
  - Cash Deposit (현금 예치)

규모: 월 평균 BSP 정산액 기준 산정
     PCC/OID 추가 시 정산 규모 변동 → 보증금 재산정 가능
```

### BSP 모니터링

```
IATA가 여행사 재무 건전성 모니터링

  정산 지연     → 경고 1단계
  반복 지연     → 경고 2단계
  미납         → Default 선언
  Default      → BSP 참여 정지 → 발권 불가

→ 정산대사 지연은 BSP Default 리스크
→ BSP Default = 사업 중단급 이슈
```

## 20. 전체 연결 맵

```
[고객]
  │ 결제 (판매가)
  ▼
[여행사 시스템]
  │ 주문/결제 데이터
  ├──────────────────────────────┐
  ▼                              ▼
[GDS: Sabre / Amadeus]         [NDC: 항공사 직접]
  │                              │
  │ PNR 생성 / 발권 (TKT)        │
  │ Booking Class (RBD)          │
  │ SSR/OSI / Queue              │
  │                              │
  ├─→ DSR (발권 데이터)            │
  │   └→ 여행사 저장소              │
  │                              │
  └─→ BSP 리포팅 ──→ [IATA BSP]   │
                      │          │
                   Billing ←─────┘
                   ADM/ACM
                   HOT/RD
                      │
                      ▼
                 [정산대사]
                 DSR vs BSP Billing
                 내부 시스템 vs DSR
                 수익 검증
                      │
                      ▼
                 [BSP Bank]
                 여행사 → BSP → 항공사

횡단 개념:
  PCC/OID: 채널 식별 → DSR 분리 → BSP 정산 분리
  Branch/EOS: PCC/OID 간 접근 권한
  Codeshare/Interline: 항공사 간 정산
  IATA 인증/보증금: BSP 참여 자격
```
